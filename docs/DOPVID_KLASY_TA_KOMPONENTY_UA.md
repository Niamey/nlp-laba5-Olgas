# Доповідь: класи та ключові компоненти проєкту

Використовуй цей файл під час захисту: **відкривай вказаний файл в IDE** і орієнтуйся на блок «Що сказати».

> **Важливо:** у Python-проєкті на LangGraph багато логіки зроблено **не класами**, а **модулями з async-функціями** (вузли графа). На захисті це нормально: скажи *«стан типізований TypedDict, поведінка — у вузлах-функціях»*. Нижче спочатку йдуть **справжні типи/класи**, потім — **логічні компоненти** (файл = тема слайду).

---

## Частина A — типи та класи даних (відкрий файл і покажи оголошення)

### 1. `IssueTriageState` — `agent/state.py`

| | |
|--|--|
| **Що це** | `TypedDict` — **схема стану** всього графа LangGraph (один «об’єкт стану» на прогін). |
| **Навіщо** | Усі вузли читають/оновлюють одні й ті самі поля: вхід (`issue_url`), дані GitHub (`fetched_issue`), докази (`tool_results`), план, звіт, `grounding_passed`, ліміти, помилки, повідомлення. |
| **Що сказати** | *«Це контракт даних між кроками агента: замість десятка глобальних змінних — один типізований стан, який перевіряється статично і зручний для чекпойнтера.»* |
| **Поруч показати** | Функцію **`initial_state(...)`** — фабрика початкового стану перед `ainvoke`. |

---

### 2. `TriageRequest` — `api.py`

| | |
|--|--|
| **Що це** | Pydantic **`BaseModel`** — тіло HTTP **POST /triage**. |
| **Поля** | `issue_url`, опційно `task_hint`. |
| **Навіщо** | Автоматична валідація типів і зручна OpenAPI-документація в `/docs`. |
| **Що сказати** | *«Це контракт API для клієнта: що саме можна надіслати на сервіс.»* |

---

### 3. `TriageResponse` — `api.py`

| | |
|--|--|
| **Що це** | Pydantic **`BaseModel`** — відповідь одразу після постановки задачі. |
| **Поля** | `job_id`, `status`, `message`. |
| **Навіщо** | Асинхронний патерн: клієнт отримує id і далі опитує результат. |
| **Що сказати** | *«Ми не тримаємо HTTP з’єднання хвилину — повертаємо ідентифікатор фонової задачі.»* |

---

### 4. `TriageResult` — `api.py`

| | |
|--|--|
| **Що це** | Pydantic **`BaseModel`** — відповідь **GET /triage/{job_id}**. |
| **Поля** | Статус, `issue_url`, `task_type`, `report`, `grounding_passed`, метрики, помилка, час створення. |
| **Навіщо** | Один стабільний JSON для фронту, Swagger, автотестів. |
| **Що сказати** | *«Це повний зріз задачі для опитування: чи готово, який тип triage, текст звіту, чи пройшов grounding.»* |

---

### 5. Об’єкт `mcp` (`FastMCP`) — `mcp_server/server.py`

| | |
|--|--|
| **Що це** | Екземпляр **`FastMCP`** з бібліотеки MCP (це **клас фреймворку**, не наш). |
| **Навіщо** | Реєструє **тулі** (`@mcp.tool`) і запускає MCP-сервер у режимі stdio. |
| **Що сказати** | *«Наш GitHub MCP — окремий процес; FastMCP дає декларативну реєстрацію інструментів і опис для LLM.»* |
| **Поруч показати** | П’ять функцій з **`@mcp.tool()`** нижче по файлу — це «методи сервера» у змісті протоколу. |

---

### 6. `app` — `api.py` (екземпляр `FastAPI`)

| | |
|--|--|
| **Що це** | Глобальний **`app = FastAPI(...)`** — не наш клас, але **точка входу веб-шару**. |
| **Навіщо** | Маршрути `/health`, `/triage`, `/jobs`, CORS, фонові задачі. |
| **Що сказати** | *«HTTP-обгортка навколо того самого `run_triage`, що й CLI — одна бізнес-логіка, два інтерфейси.»* |

## Частина B — логічні компоненти (файл = слайд; «клас» = модуль)

Тут немає `class`, але на захисті ти кажеш: **«компонент X у файлі Y»** і показуєш **головну функцію**.

### 7. Збірка графа — `agent/graph.py`

| | |
|--|--|
| **Призначення** | Збирає **LangGraph**: вузли, ребра, умовні переходи, `MemorySaver`, `interrupt_before` для HIL. |
| **Ключі** | **`build_graph()`** — головна фабрика; **`error_sink`**, **`budget_sink`** — коректне завершення при помилці/ліміті; **`_passthrough`** — технічний вузол для роутера. |
| **Що сказати** | *«Це серце оркестрації: тут видно весь сценарій від розбору URL до звіту й виходу.»* |

---

### 8. Роутинг — `agent/nodes/router.py`

| | |
|--|--|
| **Призначення** | Чисті функції **без побічних ефектів**, які повертають **ім’я наступної гілки** для conditional edges. |
| **Ключі** | **`route_after_decompose`**, **`route_by_task_type`**, **`route_after_completion`**. |
| **Що сказати** | *«Розділили маршрутизацію від бізнес-логіки вузлів — простіше тестувати й пояснювати граф.»* |

---

### 9. Розбір задачі — `agent/nodes/decompose.py`

| | |
|--|--|
| **Призначення** | Парсинг GitHub URL, витяг `owner/repo/number`, інтерпретація `task_hint`. |
| **Ключі** | **`decompose_task`**. |
| **Що сказати** | *«Перший шар без мережі — валідація входу, щоб не витрачати токени на зламані URL.»* |

---

### 10. Завантаження issue — `agent/nodes/fetch.py`

| | |
|--|--|
| **Призначення** | Отримати issue через MCP **`fetch_github_issue`**, з нормалізацією відповіді; fallback на **`github_direct`**. |
| **Ключі** | **`fetch_issue_node`**, допоміжні **`_normalize_issue_payload`**, **`_finalize_fetch`**. |
| **Що сказати** | *«Тут надійність: спочатку MCP, якщо payload зламаний — прямий REST до GitHub у тому ж процесі.»* |

---

### 11. Планування — `agent/nodes/planner.py`

| | |
|--|--|
| **Призначення** | За текстом issue визначити **`task_type`** і список кроків **`plan`**. |
| **Ключі** | **`plan_node`**, **`_format_issue_for_llm`**, константа **`PLAN_PROMPT`**. |
| **Що сказати** | *«Переводимо сирий issue у керований сценарій: який тип triage і які кроки виконати.»* |

---

### 12. Воркери — `agent/nodes/workers.py`

| | |
|--|--|
| **Призначення** | Чотири спеціалізовані кроки аналізу під тип задачі. |
| **Ключі** | **`duplicate_point`**, **`code_area_point`**, **`stale_point`**, **`classify_point`**. |
| **Що сказати** | *«Розділили сценарії: дублікат, область коду, застарілість, загальна класифікація — кожен вузол додає структуровані findings.»* |

---

### 13. Звіт і grounding — `agent/nodes/completion.py`

| | |
|--|--|

| **Що сказати** | *«Окремий крок якості: звіт не лише генерується, а ще перевіряється відносно tool results і issue.»* |

## Рекомендований порядок слайдів / демо

1. **`docs/architecture/*.svg`** — загальна картина.  
2. **`agent/state.py`** — `IssueTriageState` + `initial_state`.  
3. **`agent/graph.py`** — `build_graph` (скрол до `add_node` / `add_conditional_edges`).  
4. **`mcp_server/server.py`** — `mcp = FastMCP` + один `@mcp.tool`.  
5. **`agent/mcp_config.py`** — два сервери.  
6. **`api.py`** — три Pydantic-моделі + `triage` / `get_triage`.  
7. **`main.py`** — `run_triage`.  
8. **Термінал** — `python main.py --list-mcp` або один прогін `--no-hil`.

Якщо комісія питає «де ООП-класи» — відповідь одним реченням: *«Ми свідомо використали TypedDict для стану графа, Pydantic для API і функції-вузли для LangGraph; це стандартний стиль LangGraph, при цьому типи даних зафіксовані.»*
